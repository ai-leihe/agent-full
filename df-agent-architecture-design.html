df-agent 大型软件系统架构设计与演进规划

版本 1.0 · 2026-09-13 · 范围：df-agent 生产异常分析系统 / 指标报告系统 C4 / 部门路由 / 蓝凌知识库同步 · 编写：软件架构师

1. 背景与约束

系统现状：Flask 单体应用（端口 8001，版本 1.0.2），Docker 化部署于 Linux 服务器（python:3.11-slim-bookworm 基础镜像）。核心链路：自然语言 → NL2SQL → Impala 查询 → 异常分析/指标报告 → 部门路由（生产部 → 设备部/质量部）→ 蓝凌知识库回写。

技术资产：Impala 核心表 self_bi.module_sc_ai_indicators（value1-5 为 string 不可 SUM、month_id 格式 'YYYY-MM'）、RAGFlow（BGE-M3 + Milvus）Schema 检索、doubao-seed-2.0-pro LLM、matplotlib/reportlab 报告生成、已沉淀的 NL2SQL 提示词治理经验（date_type 显式补充、规避 SAFE_CAST/NULLIF/COALESCE、WHERE/ORDER BY 用原始列名）。

关键约束：

  • 团队规模小、边界仍在演进 → 禁止一步微服务化（No architecture astronautics）
  • Impala 慢查询与并发能力有限 → 查询必须池化、可熔断、可缓存
  • LLM 输出不确定性高 → NL2SQL 准确率依赖提示词与 badcase 沉淀，需独立治理
  • 系统已在生产运行（指标报告已部署）→ 演进必须渐进式、可回滚

2. 目标架构总览

五层结构 + 横切能力带。核心变化：Impala 访问收敛到独立查询代理层（连接池/超时/熔断/缓存），LLM 与向量检索收进 AI 能力层，应用层只保留业务编排——这是未来拆分服务的前提。

图 1 · 目标架构总览（C4 Container 视图）

分层职责说明

层职责边界原则
接入层统一入口、TLS、认证、限流、请求日志不含业务逻辑；限流保护下游 LLM 与 Impala

流程设计要点：① 步骤 2 的路由决策与步骤 3 的 SQL 生成都依赖 LLM，二者都要有置信度阈值，低置信走「反问澄清」而非硬生成；② 步骤 3 的治理规则（month_id、date_type、函数白名单）应实现为确定性代码校验器（SQL 后处理/静态检查），而不是只靠提示词约束；③ 步骤 5 的知识库回写必须异步化（重试队列），不阻塞用户主链路。

4. 架构方案权衡

面向当前团队规模与系统阶段，给出两个候选方案：

方案 A · 模块化单体（推荐起点）方案 B · 直接微服务化
思路单进程 Flask 内按领域划模块（路由/查询/分析/报告/知识库），模块间只走接口契约按服务拆分部署：查询服务、分析服务、报告服务、网关
部署现有 docker-compose 单镜像，运维成本不变需引入服务注册、网关、分布式追踪，运维复杂度陡增
演进能力模块边界清晰后，可按 Strangler Fig 逐个外移成服务一步到位，但边界尚未稳定时拆分会固化错误边界
团队匹配小团队可维护，代码审查与联调成本低需要平台工程支撑，当前人力难以长期维持
风险约束不严会退化成大泥球（需 CI 门禁强制依赖方向）分布式事务、联调、排障成本高；过早优化
结论采纳阶段一、二落地，为阶段三铺路暂缓仅在报告生成等模块出现明确扩缩容诉求时局部拆分

放弃的是什么（Trade-off）：方案 A 放弃了独立的故障隔离与按服务扩缩容能力——代价可接受，因为当前瓶颈在 Impala 查询与 LLM 稳定性，而非应用进程本身；这些瓶颈由查询代理与缓存层缓解，不需要微服务。

6. 关键架构决策记录（ADR）

ADR-001：保持模块化单体，暂缓微服务化 已采纳

背景：系统需长期演进，但团队规模小、领域边界（部门路由映射、知识库同步）仍在变化。

决策：单体内部按领域划四个模块并强制依赖方向，边界稳定后再按 Strangler Fig 拆分。

后果：失去服务级故障隔离与独立扩缩容；换取的是最低运维成本与最灵活的边界调整能力。

ADR-002：NL2SQL 采用「Schema RAG + 确定性校验器」而非模型微调 已采纳

背景：Impala 方言限制多（value1-5 为 string、不支持 SAFE_CAST/NULLIF/COALESCE、WHERE/ORDER BY 不支持别名），微调成本高且难以随表结构变化更新。

决策：Milvus 检索 Schema 与few-shot 样例供提示词使用；另建独立 SQL 校验器做规则级修正（补 date_type、month_id 格式、函数白名单拦截）。

后果：换模型/换表结构只需更新检索库与规则表；代价是需持续维护 badcase 回流机制。

ADR-003：Impala 访问收敛到独立查询代理层 已采纳

背景：Impala 并发与慢查询能力有限，pyhive/impyla 驱动有传输模式兼容问题（非 HTTP 下 PLAIN+密码不支持，需自动回退 impyla）。

决策：所有查询经统一代理——连接池、超时熔断、结果缓存、驱动回退策略集中在此层，应用层禁止直连。

后果：驱动兼容性修复与容量治理只需改一处；代价是多一跳抽象，简单查询路径稍长。

ADR-004：CI/CD 选型——腾讯 Coding DevOps 优先，BK-CI 为备选 建议中

背景：需覆盖代码管理/扫描/测试/构建/部署/冒烟/灰度全流程；团队在腾讯生态内。

决策建议：小团队起步用 Coding DevOps（一体化、上手快）；若未来要支撑几十个研发团队的自建效能平台（海量代码、多语言、高并发流水线），再评估 BK-CI 的插件化与规模能力。

后果：Coding 快速见效，但深度定制受限于平台能力；流水线配置需保持为代码（pipeline-as-code）以便迁移。

7. 风险与缓解

风险影响缓解措施
LLM 输出漂移导致 SQL 错误进入生产错误指标结论误导产线决策SQL 校验器硬拦截 + 查询结果二次校验 + 置信度阈值反问
Impala 大查询拖垮数仓全车间指标查询不可用查询超时熔断、并发上限、结果缓存、慢查询审计周报
单体模块边界退化成大泥球阶段三拆分无从下手CI 静态检查强制依赖方向；接口契约变更需评审
知识库同步失败造成数据不一致设备部/质量部看到的反馈缺失同步改异步队列 + 重试 + 对账任务（每日比对差异）
密钥/配置硬编码随镜像分发安全风险阶段二配置密钥中心化；镜像构建时扫描并阻断
