## 0. 设计总纲

### 0.1 设计目标

在不推翻现有 `agent-full` 平台架构的前提下，把它从"**知识摄取流水线内核**"扩展为"**产品级企业知识库平台**"。

**三条设计红线**：

| 红线 | 含义 |
|---|---|
| **不破坏现有抽象** | `Skill` / `Agent` / `Pipeline` / `PipelineContext` 四层抽象保持稳定，只做加法 |
| **复用而非重写** | 编排能力、插件热插拔、契约校验、沙盒试跑等既有资产全部复用 |
| **能力可插拔** | 新能力（混合检索、Rerank、向量库、解析器）全部以 Skill 形式落地，不写死 |

### 0.2 设计原则

| 原则 | 说明 |
|---|---|
| **白盒化** | 检索链路的每一步都应可见、可解释、可调整（差异化核心） |
| **契约先行** | 新增能力必须先定义产物契约，再写实现 |
| **权限前置** | 权限过滤是查询链路的第一道关卡，不是后置过滤器 |
| **默认好用** | 提供开箱即用的默认链路，用户无需理解内部抽象即可使用 |
| **可度量** | 每个关键能力都必须有对应的观测指标 |

## 1. 产品架构设计

### 1.1 总体架构：双平面 + 三入口 + 四层

```
┌────────────────────────────────────────────────────────────────────────────┐
│                           入口层（三入口）                                   │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────────────────────┐   │
│  │ 管理控制台    │   │ 知识问答端    │   │ 开放 API / SDK               │   │
│  │ (Web)        │   │ (Chat/嵌入)  │   │ (REST + Webhook)             │   │
│  └──────┬───────┘   └──────┬───────┘   └──────────────┬───────────────┘   │
└─────────┼──────────────────┼──────────────────────────┼───────────────────┘
          │                  │                          │
┌─────────▼──────────────────▼──────────────────────────▼───────────────────┐
│                            服务层（应用服务）                               │

│  用户与权限 · 运营分析 · 审计日志 · 插件市场 · 编排服务（复用现有）         │
└────────────────────────────────┬───────────────────────────────────────────┘
                                 │

│                         能力层（Skill 槽位体系）                            │

│  │  connector → parser → cleaner → enhancer → splitter → embedder      │   │
│  │                                                    → indexer         │   │
│  └────────────────────────────────────────────────────────────────────┘   │
│                                                                            │
│  ┌─── 在线查询平面 ────────────────────────────────────────────────────┐   │
│  │  rewriter → guard(权限) → retriever(dense+sparse) → fusion →         │   │

│  平台内核：Skill 注册中心 · Orchestration · PipelineRuntime · Warehouse      │
└────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 与现有 agent-full 的映射关系

| 新架构中的概念 | 复用现有资产 | 说明 |
|---|---|---|
| 离线索引平面 | `Pipeline` | 现有 `doc-ingestion` 即索引平面的雏形 |
| 在线查询平面 | 新增 `Pipeline` | 复用同一套 `Skill`/`Agent` 抽象 |
| 各处理环节 | `Skill` + `slot` | 新增槽位：`connector`、`parser`、`enhancer`、`reranker`、`rewriter`、`guard`、`generator` |
| 链路配置 | `Orchestration` | 用户可在编排工作台调整索引/查询链路 |
| 链路诊断 | `Orchestration.diagnose()` | 实时发现"缺 Reranker""缺权限守卫"等问题 |
| 检索过程可视化 | `PipelineContext` + `trace` | 天然可展示每一跳的结果与耗时 |
| 向量存储 | `warehouse` + `SearchableIndex` | 新增 pgvector / Qdrant 实现 |
| 插件发布 | `ext_plugins/` + `/api/reload` | 演进为插件市场 |
| 沙盒试跑 | `/api/skills/{name}/test` | 演进为"链路 A/B 对比测试" |

> **关键判断**：**不需要重构**。现有架构的抽象层级恰好匹配新能力，只需**新增槽位实现 + 新增服务层 + 新增入口层**。

### 1.3 八大功能模块总览

| # | 模块 | 定位 | 对应调研能力域 |
|---|---|---|---|
| **M1** | 知识采集 | 把知识从各种来源"收进来" | ① |
| **M2** | 知识加工 | 把原始文档变成"可检索的知识" | ② |
| **M3** | 知识存储 | 多形态索引与版本管理 | ③ |
| **M4** | 知识检索 | 从海量知识中"精准找到" | ④ |
| **M5** | 权限管理 | 保证"该看的能看到，不该看的看不到" | ⑤ |
| **M6** | 知识更新与生命周期 | 让知识"保持新鲜" | ⑥ |
| **M7** | 知识运营与分析 | 让管理"看得见效果" | ⑦ |
| **M8** | 智能应用 | 让知识"产生价值" | ⑧ |

## 2. 模块设计

### 2.1 M1 知识采集

**目标**：支持多源、批量、增量地把知识导入系统。

#### 功能清单

| 功能 | 说明 | 槽位 | 优先级 |
|---|---|---|---|
| 本地文件上传 | 支持 PDF/Word/Excel/PPT/TXT/MD/HTML/CSV/JSON | `local_connector` | P0 |
| 批量上传 / 文件夹导入 | 支持拖拽整个目录，保留相对路径为元数据 | `local_connector` | P0 |
| URL 网页抓取 | 单页/站点递归抓取，遵守 robots.txt | `web_connector` | P1 |
| 数据库接入 | 通过 SQL / 表名增量拉取，字段映射为 chunk | `db_connector` | P1 |
| 对象存储同步 | S3 / OSS / COS 桶同步，支持事件触发 | `oss_connector` | P1 |
| SaaS 同步 | 飞书/企微/Confluence/Notion 文档同步 | `saas_connector` | P2 |
| API 推送 | 外部系统主动推送文档 | 接口层 | P2 |
| 采集任务调度 | 定时/手动/Cron 触发，支持增量游标 | 服务层 | P1 |

#### 采集产物契约

```
connector:  (无)  →  raw_file_list
```

- `raw_file_list`：`{files: [{name, path, size, mime, source, source_id, updated_at, raw_bytes}]}`

#### 增量采集机制（关键设计）

```
每个文档维护指纹：doc_fingerprint = hash(content) + metadata_version
采集时比对：
  - 指纹不存在      → 新增
  - 指纹变化        → 更新（触发重新解析、重切片、重嵌入）
  - 指纹未变        → 跳过（零成本）
  - 源端已删除      → 标记删除（软删 → 待确认 → 硬删索引）
```

> **这是从"能导数据"到"能运营数据"的关键跃迁。**

### 2.2 M2 知识加工

**目标**：把原始文档加工成高质量的可检索单元。

#### 2.2.1 解析（Parser）

| 功能 | 说明 | 优先级 |
|---|---|---|
| 纯文本解析 | txt/md/html/csv/json/log，自动编码探测 | P0（已有） |
| PDF 解析 | 文本层抽取 + 分页元数据 | P0（已有） |
| Word 解析 | 段落 + 表格 | P0（已有） |
| Excel 解析 | 多 Sheet → 结构化文本（表头 + 行） | P1 |
| PPT 解析 | 按 Slide 分页，含备注 | P1 |
| **OCR 解析** | 扫描件 / 图片 PDF | P1 |
| **版面分析** | 多栏排版、表格结构、公式识别 | P2 |
| 音视频转写 | ASR → 文本 | P2 |

#### 2.2.2 清洗（Cleaner）

沿用现有 `cleaner` 槽位，新增：

| 实现 | 说明 | 优先级 |
|---|---|---|
| `basic_cleaner` | 控制符、空白、去重、邮箱脱敏 | 已有 |
| `markdown_normalizer` | 剥离 front-matter、还原链接 | 已有 |
| `sensitive_word_cleaner` | 敏感词掩码 | 已有 |
| `pii_cleaner` | 身份证/手机号/银行卡脱敏 | P1 |
| `boilerplate_cleaner` | 页眉页脚/水印/导航栏去除 | P1 |

#### 2.2.3 增强（Enhancer）—— **新增槽位**

| 功能 | 说明 | 优先级 |
|---|---|---|
| 元数据抽取 | 从文档中抽标题、作者、日期、部门、业务域 | P1 |
| 自动打标 | LLM 或规则生成业务标签 | P1 |
| **QA 对生成** | 从 chunk 反向生成可能的问题（提升召回） | P1 |
| 摘要生成 | 为长文档生成摘要（用于概览与路由） | P1 |
| 实体抽取 | 抽取实体与关系（为 GraphRAG 预留） | P2 |
| 上下文前缀 | 为 chunk 生成上下文说明（Contextual Retrieval） | P2 |

产物契约：

```
enhancer:  chunks →  enriched_chunks
enriched_chunks: {chunks: [{text, metadata, questions[], summary, entities[]}]}
```

#### 2.2.4 切片（Splitter）

沿用现有 `splitter` 槽位，新增实现：

| 实现 | 说明 | 优先级 |
|---|---|---|
| `recursive_splitter` | 递归字符切片（默认） | 已有 |
| `fixed_splitter` | 定长硬切 | 已有 |
| `markdown_splitter` | 按标题层级 | 已有 |
| `semantic_splitter` | 语义相似度断点 | P1 |
| `document_aware_splitter` | 按文档结构（章节/表格/QA） | P1 |
| `parent_child_splitter` | 同时产出小 chunk（检索用）与大 chunk（生成用） | P1 |
| `qa_splitter` | 按问答对切分 | P1 |

**推荐默认参数**：

| 文档类型 | chunk_size | overlap | 策略 |
|---|---|---|---|
| 通用中文文档 | 500 字符 | 80 字符 | recursive |
| 技术文档/Markdown | 按标题 | 0 | markdown |
| 规章制度 | 800 字符 | 100 字符 | document_aware |
| FAQ / 问答 | 单条 | 0 | qa |
| 长报告 | 1024 字符 | 128 字符 | parent_child |
| 代码文档 | 600 字符 | 60 字符 | recursive（分隔符含 `\n\nclass `、`\n\ndef `） |

#### 2.2.5 切片可视化管理（**高价值体验**）

> 借鉴 RAGFlow 的核心创新，融入我们的编排工作台。

| 功能 | 说明 |
|---|---|
| 切片预览 | 文档详情页展示所有 chunk 及其边界 |
| 切片编辑 | 支持合并、拆分、修改 chunk 文本 |
| 锁定机制 | 人工修改过的 chunk 标记 `locked=true`，重新索引时不被覆盖 |
| 切片质量提示 | 自动标记"过短""过长""纯表格""疑似噪声"的 chunk |
| 重切对比 | 修改切片策略后，可对比新旧切片结果再决定是否应用 |

### 2.3 M3 知识存储

**目标**：多形态索引 + 版本管理。

#### 2.3.1 存储形态

| 存储 | 用途 | 选型 | 优先级 |
|---|---|---|---|
| **向量索引（Dense）** | 语义检索 | pgvector（<100万）/ Qdrant（100万–1亿）/ Milvus（>1亿） | P0 |
| **倒排索引（Sparse）** | 关键词检索（BM25） | OpenSearch / 内置 BM25 / Qdrant sparse vector | P0 |
| **元数据库** | 文档/chunk/权限元数据 | PostgreSQL / MySQL | P0 |
| **对象存储** | 原始文件 | 本地磁盘 / S3 / OSS | P0 |
| **图数据库** | 知识图谱（可选） | Neo4j / NebulaGraph | P2 |
| **缓存** | 查询缓存 / 语义缓存 | Redis | P1 |

#### 2.3.2 向量库 Skill 实现

沿用 `SearchableIndex` 协议，新增实现：

| Skill | 后端 | 适用规模 |
|---|---|---|
| `memory_store` | 进程内 | 开发/演示（已有） |
| `pgvector_store` | PostgreSQL + pgvector | < 100 万（**推荐起步**） |
| `qdrant_store` | Qdrant | 100 万 – 1 亿 |
| `milvus_store` | Milvus | > 1 亿（**已实现**：`deploy/milvus` 本地 Standalone，集合内按 `run_id` 隔离） |
| `opensearch_store` | OpenSearch kNN | 复用已有 ES 栈 |

**关键要求**：索引必须记录并校验 `embedding_model + version + dimension`，不匹配则拒绝检索（现有 `knowledge_search` 已做校验，需保持并强化）。

#### 2.3.3 索引版本管理

| 功能 | 说明 |
|---|---|
| 索引快照 | 每次全量/增量重建生成一个版本号 |
| 版本灰度 | 新版本可先对 5% 流量生效，观察指标 |
| 一键回滚 | 指标异常可秒级切回上一版本 |
| 双写过渡 | 换 embedding 模型时，新旧索引并存，逐步迁移 |
| 索引健康检查 | 定期校验索引与元数据库的一致性 |

### 2.4 M4 知识检索

**目标**：高召回 + 高精度 + 可解释。

#### 2.4.1 检索链路（在线查询平面）

```
用户 Query
   │
   ▼
① rewriter（查询改写）        ← 多轮对话必需；短查询优化
   │
   ▼
② guard（权限守卫）★          ← 【前置过滤】注入用户权限范围
   │
   ▼
③ retriever（多路召回）
   ├── dense_retriever   → Top-50
   └── sparse_retriever  → Top-50
   │
   ▼
④ fusion（融合）              ← RRF (k=60)
   │
   ▼
⑤ reranker（重排）            ← Cross-Encoder → Top-5
   │
   ▼
⑥ assembler（上下文组装）      ← 去重、排序、Token 预算控制、引用编号
   │
   ▼
⑦ generator（生成）            ← LLM + 严格提示词
   │
   ▼
⑧ postprocess（后处理）        ← 引用溯源、拒答判断、敏感信息复核
   │
   ▼
答案 + 引用列表 + 追溯信息
```

#### 2.4.2 各环节设计要点

**① rewriter（查询改写）**

| 能力 | 说明 |
|---|---|
| 多轮指代消解 | 把"它的参数是多少"改写为完整问题 |
| 短查询扩展 | 过短查询补充上下文 |
| 多查询生成 | 复杂问题生成 2–3 个不同角度的子查询 |
| 开关可配 | 简单场景可关闭以降低延迟 |

**② guard（权限守卫）★ 关键设计**

> **权限过滤必须前置。** 在召回阶段就限定范围，而不是召回后再过滤。

```
实现方式（三选一，按向量库能力）：
A. 元数据过滤下推（preferred）
   dense:  vector_search(query, filter={tenant_id, kb_id IN [...], doc_id IN [...]})
   sparse: bm25_search(query, filter={...})
   → 过滤发生在索引内部，性能最优

B. 分区检索
   按 tenant / dept 分区，只检索有权限的分区

C. 应用层过滤（fallback）
   召回 Top-N*3，应用层过滤后再取 Top-N
   → 仅在后端不支持过滤时使用
```

**权限校验矩阵**：

| 层级 | 校验对象 | 生效时机 |
|---|---|---|
| 租户级 | `tenant_id` 强隔离 | 请求入口（从服务端认证上下文取，**禁止前端传入**） |
| 知识库级 | `kb_acl` | 请求入口 |
| 文档级 | `doc_acl` | **检索过滤条件** |
| Chunk 级 | `chunk.metadata.acl` | 检索过滤条件（继承文档权限 + 可覆盖） |
| 字段级 | 敏感字段掩码 | 生成后处理 |

**③ retriever（多路召回）**

| 召回器 | 说明 | 参数 |
|---|---|---|
| `dense_retriever` | 向量相似度召回 | top_n=50, score_threshold |
| `sparse_retriever` | BM25 关键词召回 | top_n=50, k1/b |
| `metadata_retriever` | 元数据精确匹配（型号、标签、时间） | 可选 |
| `graph_retriever` | 图谱多跳召回（V2） | 可选 |

**④ fusion（融合）**

采用 **RRF**：

```
RRF_score(d) = Σ_r  w_r / (k + rank_r(d))
k = 60（平滑常数）
w_r = 各召回器权重（默认等权，可调）
```

配置项：`fusion.weight.dense`、`fusion.weight.sparse`、`fusion.k`

**⑤ reranker（重排）**

| Skill | 模型 | 说明 |
|---|---|---|
| `bge_reranker` | BGE-reranker-v2-m3 | 私有化推荐，中文强 |
| `cohere_reranker` | Cohere Rerank | API，效果好 |
| `voyage_reranker` | Voyage Rerank | API |
| `llm_reranker` | LLM 打分 | 无专用模型时的兜底（成本高） |
| `none_reranker` | 直通 | 关闭重排 |

配置项：`rerank.enabled`、`rerank.model`、`rerank.top_n`（默认 5）、`rerank.score_threshold`

**⑥ assembler（上下文组装）**

| 能力 | 说明 |
|---|---|
| 去重 | 相同/高度相似的 chunk 去重 |
| 相邻扩展 | 命中 chunk 时补充其前后相邻 chunk（提升连贯性） |
| Token 预算 | 严格控制在模型上下文窗口内（默认占 30–40%） |
| 引用编号 | 为每个 chunk 分配 [1][2][3] 编号，便于溯源 |
| 来源标注 | 标注文件名、章节、页码 |

**⑦ generator（生成）**

提示词必须包含（经调研验证的最佳实践）：

| 要素 | 说明 |
|---|---|
| 角色设定 | 基于给定资料回答的企业知识助手 |
| **拒答指令** | "如果资料中不包含答案，必须明确回答'根据现有资料无法回答'，禁止编造" |
| 引用要求 | "回答中必须标注引用来源编号，如 [1]" |
| 格式约束 | 结构化输出（要点、步骤、表格） |
| 语言一致 | 与提问语言一致 |

**⑧ postprocess（后处理）**

| 能力 | 说明 |
|---|---|
| 引用提取 | 解析答案中的 [n] 并关联到 chunk |
| 拒答识别 | 识别模型输出是否为"无法回答" |
| 敏感复核 | 对生成内容做二次敏感词/PII 检测 |
| 置信度评估 | 依据 rerank 分数、引用数量给出可信度提示 |

#### 2.4.3 检索参数的可配置性（白盒化核心）

| 参数 | 默认值 | 可调范围 |
|---|---|---|
| `retrieval.dense.top_n` | 50 | 10–200 |
| `retrieval.sparse.top_n` | 50 | 10–200 |
| `retrieval.fusion.k` | 60 | 10–100 |
| `retrieval.fusion.weight.dense` | 1.0 | 0–2 |
| `retrieval.fusion.weight.sparse` | 1.0 | 0–2 |
| `rerank.enabled` | true | — |
| `rerank.top_n` | 5 | 1–20 |
| `rerank.score_threshold` | 0.0 | 0–1 |
| `context.token_budget` | 3000 | 500–8000 |
| `rewrite.enabled` | true | — |

> **这一整组参数应作为"检索配置档案"保存，可命名、可复用、可 A/B 对比。** 这是相对竞品的显著优势。

### 2.5 M5 权限管理

**目标**：细粒度、可审计、默认拒绝。

#### 2.5.1 权限模型

采用 **RBAC + ACL 混合模型**（ABAC 作为 V2 增强）：

```
┌──────────────────────────────────────────────────────┐
│  认证层                                               │
│  SSO / OAuth2 / LDAP / 本地账号                       │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│  租户层（强隔离）                                      │
│  tenant_id ← 从服务端认证上下文获取，禁止前端传入        │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│  组织层                                              │
│  用户 (user) → 部门 (department，树形) → 角色 (role)   │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│  资源层（ACL）                                        │
│  知识库 ACL → 文档 ACL → Chunk ACL（可选覆盖）         │
└──────────────────────────────────────────────────────┘
```

#### 2.5.2 角色与权限矩阵（默认角色）

| 角色 | 知识库 | 文档 | 检索 | 问答 | 配置 | 用户管理 | 审计 |
|---|---|---|---|---|---|---|---|
| **超级管理员** | CRUD | CRUD | ✅ | ✅ | ✅ | ✅ | ✅ |
| **知识库管理员** | CRUD（本库） | CRUD（本库） | ✅ | ✅ | ✅（本库） | ❌ | ✅（本库） |
| **知识贡献者** | 只读 | 创建/编辑（自己的） | ✅ | ✅ | ❌ | ❌ | ❌ |
| **普通用户** | 只读（有权限的） | 只读 | ✅ | ✅ | ❌ | ❌ | ❌ |
| **访客** | 仅指定库 | 仅指定文档 | ✅（受限） | ✅ | ❌ | ❌ | ❌ |
| **审计员** | 只读 | 只读 | ❌ | ❌ | ❌ | ❌ | ✅ |

权限原子：`read` / `write` / `delete` / `admin` / `share`

#### 2.5.3 权限继承与冲突规则

| 规则 | 说明 |
|---|---|
| **默认拒绝** | 未显式授权即拒绝（Deny by Default） |
| **继承** | Chunk 继承文档权限；文档继承知识库权限（若未单独设置） |
| **覆盖** | 文档级 ACL 可覆盖知识库级 ACL |
| **交集** | 用户实际可见 = 所有授权来源的**并集**；显式拒绝（deny）优先 |
| **部门继承** | 用户自动获得所属部门及其祖先部门的授权（树形向上继承） |

#### 2.5.4 权限校验位置（关键）

| 位置 | 校验内容 | 失败行为 |
|---|---|---|
| **API 入口** | 认证 + 租户 + 知识库访问权 | 401 / 403 |
| **检索前**（guard） | 文档级 / Chunk 级过滤条件注入 | 静默过滤（不暴露"存在但无权访问"） |
| **生成后** | 敏感字段掩码复核 | 掩码替换 |
| **审计** | 全量记录 | 异步写入 |

> **安全要求**：无权访问的资源，检索结果中**不得出现任何痕迹**（不能提示"有 3 条结果但您无权查看"），否则会泄露"某知识存在"这一信息。

#### 2.5.5 多租户隔离

| 隔离维度 | 方案 |
|---|---|
| 数据隔离 | 所有表带 `tenant_id`，所有查询强制注入 `WHERE tenant_id = ?` |
| 索引隔离 | 向量库按 tenant 分区 / 独立 collection（物理隔离更安全） |
| 缓存隔离 | Redis key 前缀含 `tenant_id` |
| 模型隔离 | 支持租户级独立模型配置（API Key 隔离） |
| 资源配额 | 租户级存储/调用量配额 |

#### 2.5.6 审计日志

| 记录项 | 说明 |
|---|---|
| 事件类型 | 登录、检索、问答、文档上传/下载/删除、权限变更、配置变更 |
| 字段 | 时间、租户、用户、IP、UA、动作、目标资源、结果、耗时 |
| 保留策略 | 默认 180 天，可配置；支持导出 |
| 查询 | 按用户/时间/动作/资源检索；支持异常行为告警 |

### 2.6 M6 知识更新与生命周期

**目标**：让知识"活"起来——该更新的更新，该淘汰的淘汰。

#### 2.6.1 生命周期状态机

```
    ┌──────────┐
    │  草稿     │ ← 新上传，待解析
    └────┬─────┘
         ▼
    ┌──────────┐
    │  解析中   │
    └────┬─────┘
         ▼
    ┌──────────┐   人工确认   ┌──────────┐
    │  待审核   │ ──────────▶ │  已发布   │ ──┐
    └──────────┘              └────┬─────┘   │
                                   │         │ 内容变化
                                   │         ▼
                                   │    ┌──────────┐
                                   │    │  待更新   │
                                   │    └────┬─────┘
                                   │         │ 重新索引
                                   │         └────▶ 已发布
                                   ▼
                              ┌──────────┐
                              │  已过期   │ ← 到达 expire_at 或超期未复核
                              └────┬─────┘
                                   ▼
                              ┌──────────┐
                              │  已归档   │ ← 软删除，可恢复
                              └────┬─────┘
                                   ▼
                              ┌──────────┐
                              │  已删除   │ ← 硬删除（需二次确认）
                              └──────────┘
```

#### 2.6.2 增量更新机制

| 触发方式 | 说明 |
|---|---|
| 手动 | 用户在文档列表点击"重新索引" |
| 定时 | 按数据源配置的 Cron 自动同步 |
| 事件驱动 | 对象存储事件 / Webhook 推送 |
| 内容变化检测 | 指纹比对，变化才处理 |

**更新粒度**：

| 粒度 | 说明 | 成本 |
|---|---|---|
| 文档级 | 整个文档重新解析+切片+嵌入 | 中 |
| **Chunk 级**（推荐） | 只对变化的 chunk 重新嵌入 | 低 |
| 全库级 | 整个知识库重建 | 高（用于换 embedding 模型） |

#### 2.6.3 内容新鲜度治理

| 功能 | 说明 |
|---|---|
| 有效期设置 | 文档可设 `expire_at`，到期自动标记"已过期" |
| 复核提醒 | 超过 N 天未更新的文档，提醒负责人复核 |
| 新鲜度看板 | 展示"90 天内更新文档占比"（目标 > 70%） |
| 使用度分析 | 长期零命中的文档标记为"待评估" |
| 失效检测 | 引用链接检测、源端消失告警 |

#### 2.6.4 知识审核流程（可选开启）

```
提交 → 一审（知识管理员：内容质量）→ 二审（业务负责人：业务准确性）→ 发布
```

- 支持配置审核层级（0/1/2 级）
- 审核记录留痕
- 支持批量审核
- 支持"先发布后审核"模式（宽松场景）

### 2.7 M7 知识运营与分析

**目标**：让知识库的效果"可度量、可优化"。

#### 2.7.1 运营指标体系

| 类别 | 指标 | 定义 | 目标值 |
|---|---|---|---|
| **效果** | 答案准确率 | 人工抽检/评测集判定的正确率 | **> 90%** |
| | Faithfulness | RAGAS 忠实度 | **> 0.90** |
| | Context Recall | RAGAS 上下文召回 | **> 0.85** |
| | Context Precision | RAGAS 上下文精度 | **> 0.80** |
| **效率** | 首次响应时间 | 从提问到首字输出 | **< 2s** |
| | 完整响应时间 | 从提问到答案完成 | **< 5s** |
| | 检索耗时 | 召回+融合+重排总耗时 | **< 500ms** |
| **业务** | **分流率**（Deflection Rate） | 未转人工的会话占比 | **40–60%** |
| | 自助解决率 | 用户标记"已解决"占比 | **> 60%** |
| | 好评率 | 点赞 / (点赞+点踩) | **> 85%** |
| | 拒答率 | 判定为"无法回答"的占比 | 监控项（过高=知识缺失，过低=可能幻觉） |
| | 转人工率 | 明确要求人工的占比 | 监控项 |
| **内容** | 内容新鲜度 | 90 天内更新文档占比 | **> 70%** |
| | 覆盖率 | 有命中的文档 / 总文档 | 监控项 |
| | 零命中文档数 | 长期无命中的文档数 | 监控项（用于清理） |
| **成本** | Token 消耗 | 输入/输出 token 量 | 监控项 |
| | 单次问答成本 | 总成本 / 问答次数 | 监控项 |
| | 缓存命中率 | 语义缓存命中率 | **> 20%** |

#### 2.7.2 核心分析看板

| 看板 | 内容 |
|---|---|
| **总览** | 知识库数、文档数、chunk 数、问答量、分流率、好评率（趋势图） |
| **效果分析** | RAGAS 四指标趋势、按知识库/文档类型下钻 |
| **未答问题** | Top 未答问题排行（按频次）、一键生成"待补充知识"任务 |
| **检索质量** | 零结果率、低分命中率、rerank 前后对比 |
| **内容健康** | 新鲜度分布、过期文档、零命中文档、切片质量异常 |
| **用户行为** | 活跃用户、提问分布、会话轮次、时段分布 |
| **成本** | Token 消耗趋势、按模型/租户拆分、单次成本 |

#### 2.7.3 评测服务（RAGAS）

| 功能 | 说明 |
|---|---|
| 评测集管理 | 创建/导入黄金集（`question / ground_truth / relevant_doc_ids`） |
| 评测执行 | 对指定索引版本跑全量评测，输出四指标 |
| 版本对比 | 对比两次评测结果，定位提升/退化 |
| 回归门禁 | 配置阈值，指标下降超阈值阻断发布 |
| 失败分析 | 逐条展示失败案例的检索结果与生成答案，辅助定位 |
| 自动生成评测集 | 从文档自动生成候选问答对，人工确认后入集 |

## 4. 关键交互流程

### 4.1 流程一：知识入库（管理员）

```
① 创建知识库
   填写名称/描述 → 选择 Embedding 模型 → 选择切片策略 → 设置默认权限
   ↓（实时诊断：若未选 Reranker，提示"建议启用重排以提升准确率"）

② 配置数据源
   选择类型（本地/URL/DB/S3）→ 填写配置 → 设置同步频率 → 测试连通性

③ 采集与解析
   系统自动：解析 → 清洗 → 增强 → 切片
   进度可视化，失败项可单独重试

④ 切片审核（可选）
   切片预览 → 标记问题切片 → 人工编辑 / 调整策略重切 → 确认

⑤ 向量化与索引
   批量嵌入 → 写入向量库 + 倒排索引 → 建立 ACL 索引
   完成后展示：新增 N 篇 / 更新 M 篇 / 失败 K 篇

⑥ 发布
   设置生效范围与权限 → 发布（或进入审核流）
```

### 4.2 流程二：知识问答（业务用户）

```
① 提问
   用户在问答页/IM/嵌入组件输入问题

② 鉴权与范围确定
   服务端获取 tenant_id + user_id → 解析可访问的知识库与文档范围

③ 检索
   改写 → 权限过滤 → 双路召回 → RRF 融合 → Rerank → 上下文组装

④ 生成
   LLM 生成（带引用要求与拒答指令）

⑤ 后处理
   引用溯源 → 敏感复核 → 置信度评估

⑥ 返回
   流式输出答案 + 可点击引用 + 追问推荐

⑦ 反馈
   用户点赞/点踩/标记未解决 → 进入反馈池
```

### 4.3 流程三：效果优化（知识管理员）

```
① 发现问题
   运营看板告警："未答问题 Top10 中 3 条属于产品手册"

② 定位原因
   在检索测试台复现问题 → 查看链路追踪
   → 判断是【召回缺失】还是【重排错误】还是【知识缺失】

③ 对症处理
   ├─ 召回缺失 → 调整切片策略 / 启用查询改写 / 调整 Top-N
   ├─ 重排错误 → 调阈值 / 换 Rerank 模型 / 调整融合权重
   └─ 知识缺失 → 补充文档 → 增量索引

④ 验证效果
   在检索测试台对比修改前后 → 跑评测集回归

⑤ 发布
   保存为新的检索配置档案 → 灰度生效 → 观察指标
```

## 5. 非功能需求设计

### 5.1 性能

| 场景 | 指标 | 目标 |
|---|---|---|
| 检索（召回+融合+重排） | P95 延迟 | **< 500ms** |
| 问答首字输出 | P95 延迟 | **< 2s** |
| 问答完整响应 | P95 延迟 | **< 5s** |
| 文档索引吞吐 | 并发 | ≥ 10 文档/秒（单 worker） |
| 问答并发 | QPS | ≥ 50（单实例，含 LLM 等待） |
| 单知识库规模 | 向量数 | 支持 ≥ 1000 万 |
| 单租户文档数 | 文档 | 支持 ≥ 100 万 |

### 5.2 可靠性

| 项 | 要求 |
|---|---|
| 可用性 | 99.9%（核心检索/问答链路） |
| 降级策略 | LLM 超时 → 返回检索原文；Rerank 失败 → 直通；向量库慢 → 退化为关键词检索 |
| 熔断 | 外部模型调用失败率 > 50% 时熔断 30s |
| 幂等 | 索引操作幂等，重复执行不产生脏数据 |
| 数据备份 | 元数据库每日全备 + 增量；向量库快照；支持一键恢复 |

### 5.3 安全

| 项 | 要求 |
|---|---|
| 传输加密 | HTTPS / TLS 1.2+ |
| 存储加密 | 敏感字段（API Key）加密存储 |
| 认证 | SSO / OAuth2 / LDAP / 本地账号 |
| 会话 | JWT + 刷新令牌，超时自动登出 |
| 注入防护 | SQL 参数化、Prompt 注入检测 |
| **Prompt 注入防护** | 对检索到的内容做指令清洗；系统提示词与检索内容严格分隔 |
| 越权防护 | 所有资源操作二次校验归属；禁止前端传入 tenant_id |
| 数据出境 | 私有化部署零出境；SaaS 场景支持指定区域 |

### 5.4 可观测性

| 层面 | 内容 |
|---|---|
| 日志 | 结构化日志（JSON），含 trace_id 贯穿全链路 |
| 指标 | Prometheus 指标：请求量、延迟、错误率、Token 消耗、缓存命中率 |
| 链路追踪 | 检索链路每跳耗时（已有 `trace` 基础） |
| 告警 | 错误率、延迟、拒答率异常告警 |

### 5.5 成本控制

| 手段 | 说明 |
|---|---|
| **模型分层路由** | 简单查询用小模型，复杂查询用大模型 |
| **语义缓存** | 相似问题（相似度 > 0.95）直接返回缓存答案，TTL 1–12h（不超过 24h） |
| **Embedding 缓存** | 相同 chunk 不重复嵌入 |
| **Batch 嵌入** | 批量请求降低单价与延迟 |
| **Token 预算控制** | 上下文严格限长 |
| **用量配额** | 租户/用户级配额，超限告警或限流 |
| **成本归因** | 按知识库/租户/模型拆分成本 |

### 5.6 可扩展性

| 项 | 要求 |
|---|---|
| 水平扩展 | 检索服务无状态，可水平扩展 |
| 插件机制 | 所有能力以 Skill 落地，支持热插拔（已有） |
| 多后端 | 向量库/元数据库/模型服务均可替换 |
| 国产化 | 支持国产数据库、国产芯片（ARM）、国产模型 |

### 5.7 兼容性

| 项 | 要求 |
|---|---|
| 部署 | Docker / Docker Compose / K8s；支持离线镜像部署 |
| 浏览器 | Chrome 90+ / Edge 90+ / Firefox 90+ / Safari 14+ |
| 文件格式 | 见 M1 采集模块清单 |
| 国产化 | 麒麟 / 统信 OS；达梦 / 人大金仓 数据库 |

## 6. 技术选型建议（落地层面）

| 层面 | 推荐选型 | 理由 |
|---|---|---|
| Web 框架 | FastAPI（**已有**） | 复用现有 |
| 元数据库 | PostgreSQL | 与 pgvector 同栈，运维简单 |
| 向量库（起步） | **pgvector** | 零新增组件，< 100 万向量够用 |
| 向量库（规模化） | Qdrant | 100 万–1 亿，支持 payload 过滤（权限前置必需） |
| 倒排索引 | OpenSearch / 内置 BM25 | 与向量库配合做混合检索 |
| Embedding（私有化） | **BGE-M3** | 中文强、支持稠密+稀疏、可离线 |
| Embedding（API） | text-embedding-3-large | 综合能力强 |
| Rerank | **BGE-reranker-v2-m3** | 效果与成本平衡 |
| LLM | 可配置（doubao / Qwen / DeepSeek / GPT） | 用户按需选择 |
| 缓存 | Redis | 语义缓存 + 会话 |
| 任务队列 | Celery / RQ / 内置线程池 | 索引任务异步化 |
| 前端 | 复用现有 Web（可平滑升级 Vue/React） | 减少改造量 |
