## 0. 调研背景与目标

### 0.1 项目起点

我们已有一个可运行的 **Agent 平台内核**（`agent-full`），其能力边界为：

> 文件上传 → 文件清洗 → 文本切片 → 向量化 → 向量入库 → 相似度检索

平台的核心抽象是 `Skill`（最小能力单元）/ `Agent`（Skill 串联）/ `Pipeline`（多 Agent 成链）/ `PipelineContext`（数据总线），并且支持**运行时编排**（在界面上增删阶段、跨槽位换实现、改参数、契约诊断、自动补全、方案存档）。

**这说明我们已有知识库的"摄取流水线骨架"，但距离一个"产品级知识库"还差很远。**

### 0.2 本次调研要回答的问题

| # | 问题 | 对应章节 |
|---|---|---|
| Q1 | 市面上标准的知识库产品有哪些？它们的能力边界在哪？ | 第 1 章 |

### 0.3 调研方法

- **竞品功能拆解**：以官方文档 / 开源仓库 / 产品手册为信息源，按统一维度矩阵横向对比
- **技术方案溯源**：以 RAG 领域公开的最佳实践与论文（RAGAS、GraphRAG、Hybrid Search / RRF）为依据
- **现状 Gap 分析**：以实际代码结构为准（非文档描述），逐项核对能力缺口
- **结论收敛**：输出可执行的定位建议与机会点

## 1. 竞品调研：行业知识库产品全景

### 1.1 赛道地图

知识库产品当前大致分为**四类选手**，它们的商业模式、能力深度、目标客户截然不同：

| 类别 | 代表产品 | 核心形态 | 商业模式 | 典型客户 |
|---|---|---|---|---|
| **A. 开源可私有化** | RAGFlow、MaxKB、FastGPT、BISHENG | 可 Docker 一键部署，深度可改 | 开源免费 + 企业版/技术支持 | 中大型企业、政企、数据敏感行业 |
| **B. SaaS 低代码平台** | Dify、Coze（扣子）、腾讯 ADP | 云端开箱即用，拖拽编排 | 免费额度 + 订阅 + 按量 | 中小企业、业务部门、个人开发者 |
| **C. 云厂商全栈** | 阿里百炼、火山引擎方舟、腾讯云大模型知识引擎 | 与云基础设施深度绑定 | 资源费（CU/小时）+ Token + 解析费 | 已上云企业、需要弹性扩容 |
| **D. 底层框架/组件** | LlamaIndex、LangChain、Haystack | 库/SDK，非产品 | 开源 + 云托管版 | 研发团队、需要自建 |

**我们的位置判断**：`agent-full` 目前是 **D 类（底层框架）**，但它具备"运行时编排"这一 A/B 类产品才有的交互能力。**这是一个有价值的错位——我们有机会从 D 类向上做成一款 A 类产品（可私有化 + 可编排 + 可扩展）。**

### 1.3 重点竞品深度拆解

#### 1.3.1 RAGFlow —— "文档理解能力"的标杆

- **定位**：开源 RAG 引擎，主打**深度文档理解（Deep Document Understanding）**
- **杀手锏**：
  - 自研版面分析，能处理复杂 PDF 的表格、公式、多栏排版
  - **模板化切片（Template-based Chunking）**：可视化配置切片规则，切片结果可见可改
  - **切片可视化 + 人工干预**：这是它最强的产品化能力——用户可以手动调整切片边界
  - GraphRAG 支持，能做多跳推理
- **弱点**：部署重（依赖较多）、上手门槛高、UI 偏工程化
- **对我们的启示**：**"切片可见 + 可干预"是知识库产品的高价值体验**，我们的"编排工作台"思路天然适合承载这一点。

#### 1.3.2 Dify —— "编排体验"的标杆

- **定位**：LLM 应用开发平台，知识库是其内置能力之一
- **杀手锏**：
  - 极致的拖拽式 Workflow 编辑体验
  - 知识库与 Chatflow / Agent 无缝打通
  - 插件市场生态
- **弱点**：知识库本身深度不够（文档解析弱于 RAGFlow）、大知识库检索性能一般
- **对我们的启示**：**我们的"运行时编排 + 契约诊断 + 自动补全"在知识摄取链路上比 Dify 更进一步**（Dify 主要是应用编排，不是数据流水线编排）。这是差异化点。

#### 1.3.3 MaxKB / FastGPT —— "开箱即用"的标杆

- **定位**：开箱即用的企业知识库问答系统
- **杀手锏**：国产化适配好、部署简单、与国产生态（如 FastGPT 的 OneAPI）整合好
- **弱点**：定制性一般、深度加工能力有限
- **对我们的启示**：**"一键可用"是产品化的必要条件**——我们有强大的内核，但必须提供"默认就好用"的路径，不能要求用户先理解 Slot/Skill/Pipeline。

#### 1.3.4 Coze（扣子）/ 腾讯 ADP —— "Agent 生态"路线

- **定位**：面向 C 端/B 端的 Agent 开发平台
- **杀手锏**：SaaS 生态集成极强（飞书、企微、微信、抖音等）、插件丰富
- **弱点**：私有化能力弱、知识库深度有限、数据出境/合规顾虑
- **对我们的启示**：**生态集成是知识库的"最后一公里"**——知识库只有接入业务系统（IM、工单、CRM）才能产生真实价值。

#### 1.3.5 阿里百炼 / 火山引擎 —— "云全栈 + 计费"路线

- **定位**：云厂商的模型 + 知识库一站式服务
- **杀手锏**：弹性算力、模型丰富、企业级 SLA
- **计费模式（重要参考）**：
  - **资源费**：按 CU 计费，`CU = MAX(CPU 核数, 内存GB / 8)`，按小时结算
  - **Token 费**：按输入/输出 token 分别计价
  - **解析费**：按文档页数计费（OCR / 高精度解析单独计价）
- **对我们的启示**：**私有化买断 + 订阅 + 用量叠加**是我们更适配的商业模式（见 `03-产品方案PRD.md` 第 7 章）。

### 1.4 竞品调研小结

| 结论 | 说明 |
|---|---|
| **1. 文档解析深度决定上限** | RAGFlow 靠深度文档理解建立壁垒；解析差 = 检索差 = 产品差。这是我们最需要补的短板。 |
| **2. 混合检索 + Rerank 是标配** | 几乎所有 A/B 类产品都做了。纯向量检索在大规模真实语料上 recall 不够。 |
| **3. 权限是 To B 的入场券** | 没有文档级权限，进不了中大型企业。多租户隔离是 SaaS 化的前提。 |
| **4. "切片可见可改"是高价值体验** | RAGFlow 的核心产品化创新，值得借鉴。 |
| **5. 效果可评测 = 可运营** | 能度量才能优化。RAGAS 类评测能力是产品成熟度的分水岭。 |
| **6. 编排能力是我们的差异化** | 现有平台的"运行时编排 + 契约校验 + 自动补全"在数据流水线领域是稀缺能力。 |
| **7. 最后一公里是生态接入** | 知识库必须能接入 IM / 工单 / 业务系统，否则只是"技术玩具"。 |

## 2. 技术架构调研：一个标准知识库的技术底座

### 2.1 总体架构：双平面设计

标准 RAG 知识库应分为**两个平面**，职责彻底分离：

```
┌─────────────────────── 离线索引平面（Offline Indexing）───────────────────────┐
│                                                                             │
│  数据源 ──▶ 解析/抽取 ──▶ 清洗/规范化 ──▶ 切片 ──▶ 增强(元数据/QA)           │
│                                                      │                      │
│                                                      ▼                      │
│                                             向量化(Embedding)                │
│                                                      │                      │
│                              ┌───────────────────────┴────────────────┐     │
│                              ▼                                        ▼     │
│                       向量索引(Dense)                          倒排索引(Sparse)│
│                       知识图谱(可选)                           元数据/权限索引 │
└─────────────────────────────────────────────────────────────────────────────┘
                                        ▲
                        ┌───────────────┴───────────────┐
                        │     索引版本 / 快照管理         │
                        └───────────────┬───────────────┘
                                        ▼
┌─────────────────────── 在线查询平面（Online Query）───────────────────────┐
│                                                                          │
│  用户 Query ──▶ 意图理解/改写 ──▶ 【权限过滤前置】                          │
│                                        │                                 │
│                    ┌───────────────────┴──────────────────┐              │
│                    ▼                                      ▼              │
│              向量召回(Top-N)                        关键词召回(BM25 Top-N)  │
│                    └───────────────────┬──────────────────┘              │
│                                        ▼                                 │
│                            融合 RRF 排序（Top-20）                        │
│                                        ▼                                 │
│                           Rerank 重排（Cross-Encoder → Top-5）            │
│                                        ▼                                 │
│                              Prompt 组装（3–5 条）                        │
│                                        ▼                                 │
│                                    LLM 生成                              │
│                                        ▼                                 │
│                        答案 + 引用溯源 + 无关降级                        │
└──────────────────────────────────────────────────────────────────────────┘
```

**关键设计原则（必须遵守）**：

| 原则 | 说明 |
|---|---|
| **权限过滤前置** | 权限过滤必须发生在 Rerank 与 Prompt 组装**之前**，绝不能"先检索全部、再过滤结果"。原因：① 防止无权限内容进入 LLM 上下文造成泄露；② 避免有效结果被无权限结果挤占 Top-K 名额。 |
| **离线/在线解耦** | 索引重建不应阻塞在线查询；在线查询参数调整不应触发重索引。 |
| **索引可版本化** | 支持灰度切换索引版本，出问题可回滚。 |

### 2.2 关键技术选型调研

#### 2.2.1 切片策略（Chunking）

| 策略 | 原理 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 固定长度 | 按固定字符/token 数硬切 | 快、可预测 | 割裂语义 | 日志、结构化文本 |
| **递归切分** | 按分隔符优先级回退（段→句→词） | 平衡语义与长度，**推荐默认** | 对表格/公式弱 | 通用文本 |
| 语义切分 | 先向量化，在相似度低谷处断开 | 语义连贯性最好 | 成本高、不稳定 | 高价值长文档 |
| 文档感知 | 按文档结构（标题/章节/表格）切 | 保留结构信息 | 需解析器支持 | 结构化文档 |
| Agentic 切分 | LLM 判断语义边界 | 质量最高 | 成本极高 | 高价值小体量 |

**行业推荐参数**：

- **起步配置**：`chunk_size = 512–1024 tokens`，`overlap = 10%–15%`（约 50–150 tokens）
- **中文场景**：建议按字符计，`chunk_size = 500–800 字符`，`overlap = 80–120 字符`
- **我们的现状**：`chunk_size=500, chunk_overlap=80`（中文场景下**处于合理区间**）
- **重要提醒**：切片与 Embedding 模型有强耦合——某些模型（如 BGE 系列）有推荐的最大输入长度，超出会被截断。

#### 2.2.2 Embedding 模型选型

| 模型 | 维度 | 特点 | 中文表现 | 部署方式 |
|---|---|---|---|---|
| text-embedding-3-large | 3072（可降维） | 综合能力强，MTEB 高分 | 良好 | API |
| text-embedding-3-small | 1536 | 性价比高 | 良好 | API |
| Cohere embed-v4 | 1024+ | 多语言强，支持 Matryoshka 降维 | 良好 | API |
| Voyage-3 | 1024 | 检索任务专项优化 | 中等 | API |
| **BGE-M3** | 1024 | **中文最优之一，支持稠密+稀疏+多向量** | **优秀** | 可私有化 |
| GTE-Qwen2 | 1536+ | 中文榜单领先 | 优秀 | 可私有化 |
| Snowflake Arctic Embed | 1024 | 检索效率高 | 中等 | 可私有化 |

**关键约束（必须写入产品设计）**：

> **Embedding 模型是"锁定决策"**。向量空间由模型决定，一旦上线后更换模型，**必须对全量知识重新嵌入**。因此：
> 1. 知识库应记录 `embedding_model + version + dimension` 三元组；
> 2. 索引必须与 embedding 模型绑定，检索时校验一致性（我们的 `knowledge_search` 已经做了这一点：`embedder_name` 不匹配直接报 500——**这是正确的设计**）；
> 3. 提供"换模型迁移"工具链（后台重嵌 + 双写灰度）。

**推荐**：私有化场景选 **BGE-M3**（中文强、可离线、支持混合检索所需的稀疏向量）；SaaS/API 场景选 **text-embedding-3-large**。

#### 2.2.3 混合检索（Hybrid Search）与 RRF

**为什么必须做混合检索？**

- **纯向量检索的弱点**：对**精确匹配类查询**（产品型号、错误码、人名、专有名词、缩写）表现差。例如查 `ERR-4021`，语义向量会把它和一堆"错误"混在一起。
- **纯关键词检索的弱点**：无法处理同义改写、语义泛化。查"怎么报销"匹配不到"费用申请流程"。

**融合算法：RRF（Reciprocal Rank Fusion）**

```
RRF_score(d) = Σ over all rankers r:  1 / (k + rank_r(d))
```

其中 `k` 为平滑常数（通常取 60）。RRF 的优点：
- **无需归一化**——直接融合排名，避开"向量距离"和"BM25 分数"量纲不可比的问题
- **鲁棒性强**——对单个召回器的异常分数不敏感
- **实现简单**——几行代码

**替代方案**：加权分数融合（需归一化）、Convex Combination。**推荐优先用 RRF**。

#### 2.2.4 Rerank 重排

| 类型 | 原理 | 速度 | 精度 |
|---|---|---|---|
| Bi-Encoder（召回用） | Query 和 Doc 分别编码，算余弦 | 快（可预计算） | 一般 |
| **Cross-Encoder（重排用）** | Query + Doc 拼接后过模型 | 慢（不可预计算） | **高** |

**标准流水线**：

```
全库 (10万+)  ──[向量+BM25 召回]──▶  Top-50  ──[Rerank]──▶  Top-5  ──▶  LLM
```

**为什么必须 Rerank？** 召回阶段为了不漏（高 Recall），必然引入噪声；Rerank 阶段负责"精挑"（高 Precision）。经验数据：**引入 Rerank 后，LLM 答案准确率通常提升 10–25 个百分点**，是投入产出比最高的优化项之一。

**常用 Rerank 模型**：BGE-reranker-v2-m3（可私有化）、Cohere Rerank、Voyage Rerank、Qwen-Ranker。

#### 2.2.5 向量数据库选型

| 规模 | 推荐方案 | 理由 |
|---|---|---|
| < 100 万向量（原型/小规模） | **pgvector** | 复用已有 PostgreSQL，运维成本为零 |
| 100 万 – 1 亿 | **Qdrant / Weaviate** | 性能与运维平衡点，支持过滤与多租户 |
| > 1 亿 | **Milvus / Pinecone** | 分布式扩展能力 |
| 仅原型验证 | Chroma | 零配置起步 |
| 企业已用 ES/OpenSearch | OpenSearch kNN | 复用现有栈，且天然支持 BM25 混合检索 |

**我们的现状**：`warehouse.py` 是**进程内内存实现**（`memory_store`），并已声明 `SearchableIndex` 协议。

> **这是一个良好的架构决策**——协议已抽象，替换为 pgvector / Qdrant 只需新增一个 `Skill` 实现（README 第 9 节也明确列了这条扩展路线）。产品设计应沿用此路径，**不做破坏性改造**。

#### 2.2.6 检索增强技术

| 技术 | 原理 | 收益 | 成本 |
|---|---|---|---|
| **Parent-Document Retrieval**（small-to-big） | 用小 chunk 检索，返回其所属的大 chunk / 整节 | 上下文更完整，减少"断章取义" | 需维护 chunk↔parent 映射 |
| **HyDE** | 让 LLM 先生成假想答案，再用它检索 | 提升语义匹配（尤其短查询） | 每次查询多一次 LLM 调用 |
| **Multi-Query** | LLM 生成多个改写查询，分别检索后合并 | 提升召回率 | 多路检索成本 |
| **Query Rewrite** | 结合对话历史改写查询 | 多轮对话必需 | 一次 LLM 调用 |
| **Contextual Retrieval** | 为每个 chunk 生成上下文前缀再嵌入 | 显著降低检索失败率 | 索引期 LLM 成本大增 |

**建议节奏**：MVP 只做 **Query Rewrite（多轮对话必需）**；V1 加 **Parent-Document**；V2 视评测结果决定是否上 HyDE / Contextual Retrieval。

#### 2.2.7 知识图谱（GraphRAG）

**微软 GraphRAG 的核心流程**：

1. **实体-关系抽取**：用 LLM 从文本中抽取实体和关系
2. **Leiden 社区聚类**：对图做层次化社区划分
3. **社区摘要生成**：为每个社区生成摘要
4. **双模式检索**：
   - **Local Search**：针对具体实体的问答
   - **Global Search**：针对"整体主题/趋势"的问答（传统 RAG 几乎做不了）

**效果与代价（关键数据）**：

| 指标 | GraphRAG | 传统 RAG |
|---|---|---|
| 多跳推理成功率 | ~85% | ~40%（失败率） |
| 单跳事实问答 | 相当 | 相当 |
| **索引成本** | **传统 RAG 的 10–50 倍** | 基准 |
| 其中图抽取占比 | **约 75%** | — |
| 查询延迟 | 较高 | 低 |

**结论与建议**：

> **GraphRAG 不是默认选项，而是"高价值知识域的增量能力"。**
>
> 建议作为 **V2 的可选增值模块**，且只对以下场景启用：
> - 需要跨文档多跳推理（如"哪些设备故障与哪些工艺参数相关"）
> - 需要全局主题归纳（如"这批客诉的共性问题是什么"）
> - 知识域边界清晰、体量可控（1 万–10 万文档）
>
> **不要全量启用**——成本会失控。

#### 2.2.8 评测体系（RAGAS）

**RAGAS 四大核心指标**：

| 指标 | 衡量什么 | 计算方式（概念） | 目标值 |
|---|---|---|---|
| **Faithfulness**（忠实度） | 答案是否忠于检索到的上下文（防幻觉） | 答案中的陈述能被 context 支持的比例 | **> 0.90** |
| **Answer Relevancy**（答案相关性） | 答案是否切题 | 由答案反推问题，与原始问题比相似度 | **> 0.85** |
| **Context Precision**（上下文精度） | 检索到的 chunk 中有多少是真正有用的 | 相关 chunk 在排序中的位置加权 | **> 0.80** |
| **Context Recall**（上下文召回） | 需要的信息是否都被检索到 | 参考答案中的信息点在 context 中的覆盖率 | **> 0.85** |

**评测集构建方法（产品必须支持）**：

1. **黄金集（Golden Set）**：由业务专家标注 100–500 条 `(问题, 标准答案, 相关文档)` 三元组
2. **难负例（Hard Negatives）**：与正确答案语义相近但实际不相关的样本，用于压测精度
3. **分层抽样**：按文档类型、问题类型（事实型/推理型/对比型/拒答型）分层
4. **持续回归**：每次索引更新/模型切换跑一遍，指标下降超阈值则阻断发布

> **这是产品成熟度的分水岭。** 没有评测，就无法回答"改了之后是变好了还是变差了"。

### 2.3 技术调研小结

| 结论 | 我们的行动 |
|---|---|
| 双平面架构是标准做法 | 沿用；现有流水线即索引平面，需新增查询平面 |
| 混合检索 + RRF 是标配 | **MVP 必做** |
| Rerank ROI 最高 | **MVP 必做** |
| Embedding 是锁定决策 | 索引绑定模型三元组（现有设计已正确，需强化） |
| 切片策略需可分文档类型配置 | 复用现有 slot 机制，扩充实现 |
| 向量库走协议替换路线 | 沿用 `SearchableIndex`，新增 pgvector / Qdrant 实现 |
| GraphRAG 成本高 | 放 V2，作为可选增值模块 |
| RAGAS 评测是分水岭 | 纳入 V1 核心能力 |
| 权限必须前置过滤 | 设计为查询平面的**第一道关卡** |

## 3. 用户与场景调研

### 3.1 目标用户画像

| 角色 | 核心诉求 | 痛点 | 关键功能 |
|---|---|---|---|
| **知识管理员**（内容运营） | 知识能被快速、完整地灌进来并保持新鲜 | 上传麻烦、切片不可控、内容过期无人管 | 多源采集、切片可视化、生命周期治理、增量更新 |
| **业务用户**（一线员工） | 一句话问到准确答案 | 搜不到、答不准、不知道信不信 | 对话问答、引用溯源、反馈按钮 |
| **AI 应用开发者** | 快速接入、可定制、可控成本 | 黑盒、无法调参、成本失控 | 开放 API、检索参数可调、编排能力、用量看板 |
| **IT / 安全负责人** | 数据不越权、可审计、可私有化 | 权限形同虚设、无法审计 | 细粒度权限、审计日志、私有化部署 |
| **业务负责人**（管理者） | 看到投入产出 | 无法度量效果 | 运营看板、分流率、CSAT |

### 3.2 典型场景

| 场景 | 描述 | 对产品的要求 |
|---|---|---|
| **S1 内部客服/IT 支持** | 员工问"VPN 怎么连"、"报销流程是什么" | 高准确率、权限隔离（HR/财务文档分级）、接 IM |
| **S2 售后服务/技术支持** | 客户问题 → 查产品手册/FAQ/SOP | 多源同步、精确匹配（型号/错误码）、引用溯源 |
| **S3 研发知识管理** | 查接口文档、技术方案、历史故障 | 代码块友好切片、精确匹配、版本管理 |
| **S4 销售赋能** | 查产品资料、报价政策、竞品对比 | 权限严格（价格敏感）、时效性强 |
| **S5 合规/法务问答** | 查制度条款、合规要求 | 高忠实度（不能编）、必须溯源、审计日志 |
| **S6 生产制造知识** | 设备故障处置、工艺参数查询 | 结构化数据融合、多跳推理、（设备-工艺-缺陷关联） |

> **S6 与本用户实际业务（光伏生产异常分析）高度契合**——这是"多跳推理"需求最真实的落点，也是 GraphRAG 的合理应用场景。

### 3.3 用户对"好知识库"的评价标准

从行业实践与用户反馈中提炼出**五条评价轴**：

1. **答得准**（最重要）：不编造，答不上来要明确说"不知道"
2. **找得到**：同义改写、精确关键词、模糊描述都能命中
3. **信得过**：每个答案都能点开看到原文出处
4. **管得住**：不同人看到不同内容，敏感信息不外泄
5. **看得见**：管理者能看到用了多少、解决了多少、哪些没答上

### 3.4 场景调研小结

| 洞察 | 产品含义 |
|---|---|
| 用户不关心技术，只关心"答得准不准" | 产品必须把技术能力包装成"效果承诺"，而非参数 |
| 权限不是"高级功能"而是"准入条件" | 权限必须 MVP 就设计好，后补等于重构 |
| "答不上来"的处理比"答对"更能建立信任 | 必须有**拒答机制**与**兜底转人工** |
| 场景 S6（生产制造）是本团队优势场景 | 可作为差异化深耕方向（多跳推理 + 结构化数据） |

## 5. 调研结论与机会点

### 5.1 核心结论

1. **我们的内核优于竞品，产品化落后于竞品。**
   现有平台的编排能力（运行时调整 + 契约诊断 + 自动补全）在数据流水线领域是稀缺的，但缺少"用户能直接用的产品外壳"——采集、对话、权限、看板。

2. **必须补的四块地基：混合检索、Rerank、权限、持久化向量库。**
   这四项不做，产品无法交付给真实企业。

3. **差异化在"可编排的 RAG 流水线"。**
   竞品大多把检索链路做成黑盒（最多暴露几个滑杆）；我们可以让用户**看到并调整整条链路**，甚至按文档类型配置不同链路。这是从"能用"到"能调优"的跃迁。

4. **场景上应选择一个纵深方向打透。**
   泛知识库红海，但"生产制造 / 设备运维知识 + 多跳推理"是竞品薄弱且我们有业务积累的方向。

### 5.2 产品定位建议

> **定位**：一款**可私有化部署、链路可编排、效果可度量**的企业级 RAG 知识库平台。
>
> **一句话价值主张**：把 RAG 流水线从"黑盒"变成"白盒"——每一条链路都可看见、可调整、可评测。

**目标客群**：中型及以上企业（100–5000 人），有数据私有化要求，有 AI 应用开发能力或需求。

**竞争策略**：
- **对 RAGFlow**：我们能编排，它不能 → 打"灵活性"
- **对 Dify**：我们索引链路更深、可评测 → 打"专业性"
- **对 MaxKB/FastGPT**：我们切片/检索链路可视可控 → 打"可调优"
- **对云厂商**：我们可私有化、无数据出境 → 打"合规"

### 5.3 机会点清单

| 机会点 | 描述 | 价值 |
|---|---|---|
| **O1 白盒 RAG 流水线** | 检索链路完全可见、可调、可 A/B | 高（差异化核心） |
| **O2 切片可视化与人工干预** | 借鉴 RAGFlow，但融入我们的编排工作台 | 高（体验壁垒） |
| **O3 效果评测闭环** | 内置 RAGAS + 黄金集管理 + 回归门禁 | 高（信任壁垒） |
| **O4 分层检索策略** | 按文档类型/业务域配置不同链路 | 中高（实用） |
| **O5 制造场景纵深** | 结构化数据 + 图谱 + 多跳推理 | 中（垂直壁垒） |
| **O6 插件市场** | 复用现有热插拔机制做生态 | 中（长期） |

| # | 问题 | 建议 |
|---|---|---|
| 1 | 是否坚持纯私有化，还是同时做 SaaS？ | 先私有化（匹配现有部署形态），SaaS 预留多租户设计 |
